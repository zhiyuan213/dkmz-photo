## 一、要验证的三个假设

整个产品的技术方案建立在三个假设上，任何一个不成立，方案都要改。

| # | 假设 | 不成立的后果 |
|---|---|---|
| 1 | 微信 `wx.createInferenceSession` 能跑 MODNet 的 ONNX 模型（算子兼容） | 端上抠图路线作废，只能用云端 API（有成本 + 需上传用户照片） |
| 2 | 中低端手机上单张推理耗时在可接受范围（目标 ≤ 3 秒） | 用户体验崩，需降分辨率或换更小的模型 |
| 3 | 抠图边缘质量够得上报名照标准（发丝、肩线不穿帮） | 需要加边缘柔化/手动微调，或降级云端 |

**假设 1 已用静态分析完成（见第二节），假设 2、3 必须真机实测。**

## 二、已完成：模型算子兼容性静态检查

用 `scripts/inspect-model.py` 拆开模型，逐算子比照微信官方
[算子支持列表](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/inference/supports.html)。

### 结论

| 模型 | 体积 | 算子兼容 | 结论 |
|---|---|---|---|
| `model.onnx`（fp32） | 24.7 MB | ✅ 全部支持 | 可用，但下载偏大 |
| `model_fp16.onnx`（fp16） | **12.4 MB** | ✅ 全部支持 | **✅ 首选** |
| `model_quantized.onnx`（int8 动态量化） | 6.3 MB | ❌ 含 3 个不支持算子 | **❌ 不可用** |

### ⚠️ 一个真实踩坑（已规避）

网上流传的「int8 量化模型只有 6MB，最适合端上」在这里**不成立**。该模型用的是
ONNX Runtime 的动态量化，包含：

```
DynamicQuantizeLinear  x69   ← 不在微信支持列表
ConvInteger            x69   ← 不在微信支持列表
MatMulInteger          x2    ← 不在微信支持列表
```

微信的算子列表里只有 `FakeQuantize`，对应的是 **QDQ 静态量化**（产出
`QuantizeLinear` / `DequantizeLinear`）。所以：
**如果后续需要更小的模型，要做 QDQ 静态量化 + 校准数据，不要用 ORT 的动态量化。**

### 模型接口（已确认，无需再猜）

```
输入: name='input'    shape=[batch, 3, height, width]   float32   ← 动态轴
输出: name='output'   shape=[batch, 1, height, width]   float32
opset: 11
```

预处理参数（取自官方 `preprocessor_config.json`，代码里已严格对齐）：

```
短边缩到 512，宽高均取 32 的倍数
rescale 1/255 → normalize mean=0.5 std=0.5
⇒ 等价于 x / 127.5 - 1
```

## 四、跑起来（三步）

### Step 1 · 导入项目

微信开发者工具 → 导入项目 → 目录选工程根目录 `dkmz-photo`（**不是** `miniprogram`）。

- **AppID**：填「登科喵」那个小程序的 AppID；没有就选「测试号」
- 进去后打开 **详情 → 本地设置 → 勾选「不校验合法域名、web-view、TLS 版本以及 HTTPS 证书」**
  （不勾会因 `downloadFile` 域名未备案而失败）

### Step 2 · 起本地模型服务

```bash
cd dkmz-photo
node scripts/serve-models.mjs
# 模型静态服务已启动 → http://127.0.0.1:5178/model_fp16.onnx
```

### Step 3 · 页面操作

1. 「模型档位」保持默认 **本地开发服务器 · 127.0.0.1:5178**
2. 点「**下载并加载模型**」—— 走完下载进度后应显示「已加载 xx ms」
3. 「推理短边」先选 **384**（第一次别上 512，先看速度）
4. 点「**选照片 → 抠图 → 换底**」，选一张**半身/正面照**
5. 看三张图：原图 / alpha 蒙版（黑白）/ 换底结果

> 顺手上真机前，把模型换到 HTTPS 公网地址（对象存储 / CDN），并在 mp 后台
> 「开发管理 → 开发设置 → 服务器域名 → downloadFile 合法域名」里加上该域名。

## 五、通过标准（不达到就不进阶段 1）

| 指标 | 线 |
|---|---|
| 模型加载 | 成功，无报错 |
| 推理耗时（短边 384，中端安卓） | ≤ 2000 ms |
| 推理耗时（短边 512，中端安卓） | ≤ 4000 ms |
| 边缘质量 | 发丝有轻微损失可接受；**肩线、耳侧不能出现明显白边或缺块** |
| 导出体积 | 295×413 JPG ≤ 200 KB（教资笔试要求） |
| 输入分辨率 | 一张 3000×4000 的原图进来不崩、不 OOM |

**判定**：三条全过 → 端上方案成立，进入阶段 1；
边缘质量不过 → 保留端上做初筛 + 云端做精修（混合）；
推理卡在 5 秒以上 → 降到短边 256 或换更小 backbone，实在不行转云端。

## 六、失败排查表

| 现象 | 原因 | 处理 |
|---|---|---|
| `createInferenceSession 调用失败` | 基础库 < 2.30.0 | 开发者工具 → 详情 → 本地设置 → 调试基础库选 3.x |
| `模型下载失败` / HTTP 403 | 没勾「不校验合法域名」，或 URL 不对 | 勾上；或确认本地服务在跑 |
| `输出节点名不匹配` | 换了别的模型 | 用 Netron 看输出名，调 `matting.setIONames(input, output)` 的默认值 |
| 蒙版全黑 / 全白 | 输出是 logits | 代码已自动判值域并套 sigmoid，页面会显示「已按 logits 套 sigmoid」 |
| 加载即失败、提示算子不支持 | 用了 int8 动态量化模型 | 换 fp16 档位（见第二节结论） |
| 推理超时 / 小程序闪退 | 短边太大或内存不足 | 降到 256/384；换 fp32 档位试（fp16 某些机型可能不友好） |
| VisionKit 报「检测超时」 | 个别机型不回 `updateAnchors` | 换 modelMode 0（小模型）再试，或换机型 |

## 九、与阶段 1 的衔接

这个 demo 里已经有两块可以直接搬进正式项目的代码：
